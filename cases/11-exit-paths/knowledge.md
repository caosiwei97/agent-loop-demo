# 输出截断恢复

## 核心概念

第三种"作死"更隐蔽：**模型的话说到一半被截了。** 每个模型都有 `max_output_tokens` 限制（Claude 默认 8192）。如果模型要说的话超过限制，输出被硬截断。问题是：**模型自己不知道被截了**——它以为说完了，但后面还有半句话没说出来。

如果截断发生在工具调用的 JSON 中间——JSON 不完整，解析直接失败，Agent 不知道该干什么。

## 关键要点

- **Step 1：静默提高上限**（8192 → 65536）。对用户完全透明，不显示任何错误提示
- **Step 2：注入恢复消息**（最多 3 次）。恢复指令是渐进式的：
  - 第一次："直接从断点继续——不要道歉，不要回顾。把剩余工作拆成更小的块。"
  - 后续："再次被截断。大幅精简，只列关键结论。"
- **Step 3：认栽**。3 次恢复都不行，返回不完整结果，标记为"输出被截断"
- 恢复消息的讲究："不要道歉"（浪费 Token）、"不要回顾"（浪费 Token）、"从断点继续"（高效）

## 代码解析

本案例模拟了三步恢复过程：

```javascript
// 恢复消息模板
const recoveryMessages = [
  '直接从断点继续——不要道歉，不要回顾。把剩余工作拆成更小的块。',
  '再次被截断。大幅精简，只列关键结论。',
  '第三次截断。只输出最关键的结论。',
];
```

每次检测到 `finishReason === 'length'` 时，注入下一条恢复消息。如果 3 次后还是截断，则进入"认栽"步骤。

## 延伸思考

- 为什么不无限重试？如果模型在 64K 限制下连续 3 次都说不完，说明了什么？
- "不要道歉"和"不要回顾"的指令真的有效吗？模型是否总能遵守？有没有更可靠的方式？
